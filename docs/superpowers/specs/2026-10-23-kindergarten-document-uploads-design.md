# GrowLog 保教单与每周菜单图片上传设计

- 日期：2026-10-23
- 状态：待用户确认
- 资料归属：具体孩子
- 选定存储：VPS 本机持久卷保存图片，PostgreSQL 保存元数据

## 1. 意图

家长会从幼儿园收到按日发布的保教单和按周发布的菜单。GrowLog 需要在设置中提供低频管理入口，让管理员为具体孩子上传这些图片，并能在手机上按日期查看历史图片。保教单每个孩子每天最多一份，菜单每个孩子每个自然周最多一份。

## 2. 目标与成功标准

1. 设置首页增加“幼儿园资料”入口，进入后先选择孩子。
2. 页面分别提供“上传保教单”和“上传每周菜单”操作；保教单选择资料日期，菜单选择所属周。
3. 同一孩子、同一类型、同一日期或周只有一条有效资料；再次上传会替换图片并写入更新审计。
4. 历史资料按时间倒序显示缩略预览、资料日期或周范围、原文件名和更新时间；点击图片可查看适合手机屏幕的完整图片。
5. 图片与元数据都按已登录家庭隔离，图片 URL 不能绕过认证；API 和图片响应不被浏览器或 Service Worker 持久缓存。
6. Docker Compose 部署后图片存放于持久卷，容器重建不丢失；部署文档说明图片卷的备份与恢复方式。

## 3. 非目标与反目标

- 本轮不识别图片文字，不把图片内容自动写入饮食或健康记录。
- 不提供公开分享链接、匿名图片 URL 或第三方 CDN。
- 不支持 PDF、HEIC、视频或任意文件；避免手机浏览器兼容问题和不受控文件解析。
- 不支持一份资料包含多张图片；一条资料对应一张图片。需要多页时由用户先合成为一张长图，后续可独立扩展多附件模型。
- 不把图片写入 JSON/CSV 导出，也不把二进制塞入 PostgreSQL。
- 不向审计日志写入图片内容、原文件名或存储路径。

## 4. 考虑过的方案

### 方案 A：VPS 持久卷 + PostgreSQL 元数据（已选择）

图片写入应用容器挂载的专用持久卷，数据库只保存归属、周期、类型、MIME、大小、原文件名和不可预测存储键。它最适合当前单机、1G 内存 VPS：没有额外服务，数据库不会被图片放大，查看仍由应用完成认证。代价是数据库与图片卷必须一起备份。

### 方案 B：PostgreSQL 保存图片二进制

事务和备份路径统一，但手机照片会迅速放大数据库、数据库内存压力与 dump 恢复时间，不适合当前资源边界。

### 方案 C：S3 兼容对象存储

更适合多实例和大量文件，但引入外部服务、凭据、费用或额外容器。本轮单机部署不需要这部分复杂度。

## 5. 数据模型与周期规则

新增 `KindergartenDocument`：

- `id`
- `householdId`、`childId`
- `type`：`DAILY_CARE_SHEET` 或 `WEEKLY_MENU`
- `periodStart`：PostgreSQL `date`
- `originalFileName`
- `storageKey`
- `mimeType`
- `sizeBytes`
- `createdAt`、`updatedAt`

唯一约束为 `(householdId, childId, type, periodStart)`。保教单的 `periodStart` 就是所选家庭日；菜单 POST 的 `date` 可以是该周任意一天，服务端将它归一到周一，页面显示周一至周日的范围。输入必须是严格存在的 `YYYY-MM-DD` 日期，归一化使用 UTC 安全的纯日期运算，不能受浏览器、Node 进程时区或跨年边界影响。这里的“周”固定采用周一开始，避免受区域设置影响。

资料采用直接替换，不使用健康记录的软删除/恢复模型：新文件成功写入并完成数据库更新后，旧文件才被删除。页面提供显式删除并写入 `DELETE` 审计，删除后同一周期可重新上传。审计只记录字段名、资料类型与周期，不记录文件名、路径或内容。

## 6. 文件存储与一致性

新增文件存储接口，生产适配器使用 `UPLOAD_DIR`（默认 `/data/uploads`）。实际文件名由服务器生成随机 UUID 和受控扩展名，不使用用户文件名拼接路径。目录不放在 `public/` 下。

上传顺序：

1. 验证会话、来源、CSRF、孩子归属、资料类型和周期。
2. 在调用 `request.formData()` 前读取并限制请求流，multipart 请求总大小上限为 11 MiB；即使缺少或伪造 `Content-Length` 也只能在该内存边界内读取。`Content-Length` 仅用于提前拒绝，解析后再次检查真实文件字节数。
3. 只允许一个 `image` 字段，拒绝空文件或多个图片字段。声明 MIME 必须与文件魔数一致，只接受 JPEG、PNG、WebP，单文件上限 10 MiB；不信任扩展名。
4. 将新文件写入同目录临时文件，再原子重命名为随机存储键。
5. 使用 PostgreSQL `Serializable` 事务读取当前行、创建或更新元数据并写审计；对可重试的序列化/唯一冲突作有限重试。事务返回本次观察到的旧存储键，数据库失败时删除新文件。
6. 替换提交成功后仅删除该事务观察到的旧文件；失败只会留下不可访问的孤立文件，不会让数据库指向未写入文件，并记录不含敏感内容的服务器错误。并发替换采用最后成功提交者生效，所有成功提交都有对应审计。

删除同样使用可重试的 `Serializable` 事务移除数据库记录并写审计，提交后再尽力删除事务读取到的文件。GET 在替换提交前读取旧文件，提交后读取新文件；随机键保证两个版本不会互相覆盖。未来可增加孤立文件清理命令；本轮不自动扫描目录。

## 7. API 与安全

新增路由：

- `GET /api/kindergarten-documents?childId=...`：返回该孩子的元数据列表，不返回存储路径。
- `POST /api/kindergarten-documents`：接收 `multipart/form-data`，字段为 `childId`、`type`、`date`、`image`，创建或替换。
- `DELETE /api/kindergarten-documents/[documentId]`：删除资料。
- `GET /api/kindergarten-documents/[documentId]/image`：按家庭读取并返回图片。

所有写操作复用现有会话、同源和 CSRF 保护。所有查询同时按 `householdId` 和 `child.deletedAt = null` 限制；删除儿童后不能再列出、上传或查看其资料。图片响应使用数据库中验证过的 MIME，设置不带用户文件名的 `Content-Disposition: inline`、`X-Content-Type-Options: nosniff`、`Cache-Control: private, no-store`。错误保持现有 problem envelope，不泄露绝对路径、存储键或跨家庭记录是否存在。

原文件名只用于经过转义的界面显示；限制为 255 个字符并移除控制字符。服务端日志不得记录 multipart 内容、文件名、资料图片、会话或 CSRF 值。

## 8. 设置页面与移动端交互

设置首页“儿童与记录”分组新增“幼儿园资料”菜单项，使用现有文件/图片风格的线性图标，链接到 `/settings/kindergarten-documents`。

资料页包含：

1. 孩子选择器；没有孩子时显示前往“添加孩子”。
2. 两个紧凑上传面板：保教单面板选择日期，菜单面板选择所属周日期。选择文件后显示本地预览、文件名和大小，提交按钮分别为“上传保教单”和“上传每周菜单”。
3. 两个历史区块，按周期倒序显示卡片。卡片使用认证图片接口作为图片源，并以 `updatedAt` 版本参数强制替换后重新获取，显示日期或周范围、更新时间和“替换/删除”操作。
4. 点击图片打开原生 `<dialog>` 大图查看器；支持关闭按钮、Escape、焦点返回和适合触摸缩放的图片布局。若浏览器不支持 dialog，图片链接仍可在认证接口中直接打开。

上传、替换、删除均显示 pending、成功和错误状态。重复周期上传前明确提示“将替换现有图片”；删除需要确认。表单控件继续满足 16px 输入文字、44px 触控目标、亮暗主题和 320px 无页面级横向溢出。

## 9. 部署、备份与恢复

Compose 为应用增加 `uploads_data:/data/uploads` 命名卷和 `UPLOAD_DIR=/data/uploads`。镜像在运行阶段创建目录；容器重建继续挂载原卷。

数据库和图片卷必须组成一组协调备份：备份脚本先暂停应用写入，以同一个 UTC 备份 ID 生成 PostgreSQL custom dump、图片 tar、各自 SHA-256 与包含文件名/校验值的 manifest，然后恢复应用。图片 tar 路径必须相对、禁止 `..` 和绝对路径。恢复验证先校验 manifest 和两个文件，再把数据库恢复到独立验证库、把图片安全解压到独立验证目录，并通过验证配置启动应用完成一次认证图片读取；恢复到主数据库/主卷继续要求显式破坏性开关和停机。部署文档明确：只恢复数据库会保留资料条目但图片不可用，只恢复图片会产生不可访问孤立文件。

## 10. 测试与验收

### 自动化

- 周一归一化、日期与文件校验、文件名清理。
- 存储适配器原子写入、读取、删除和路径安全。
- PostgreSQL 唯一周期、家庭/孩子隔离、已删除孩子拒绝、创建/替换/删除审计、并发替换和删除竞态。
- Route Handler 的匿名、CSRF、跨家庭、缺少/伪造 `Content-Length` 的超限流、多个图片字段、错误 MIME/魔数、创建、替换、查看与删除。
- 设置入口、无孩子状态、上传表单、预览、替换提示、历史卡片和大图查看器。
- Compose 持久卷、服务端安全头、Service Worker 不缓存图片 API。

### 发布门禁

- 干净测试数据库应用新迁移。
- 完整 PostgreSQL 测试、Lint、严格类型检查和生产构建通过。
- 320、390、430、768 px 的亮暗主题浏览器检查覆盖：无孩子、上传两类图片、同周期替换、跨周列表、图片查看、删除、刷新后持久存在、固定底栏不遮挡和无页面级横向溢出。
- Docker Compose 验证上传后重建应用容器，图片仍可查看；协调备份生成后完成数据库与图片的独立恢复，并通过认证接口读回同一图片。

## 11. 验收标准

1. 管理员能在设置中为具体孩子分别上传保教单和每周菜单。
2. 每个孩子每天最多一份保教单，每个周一周期最多一份菜单；重复上传稳定替换且不产生两个数据库条目。
3. 列表与大图查看均要求有效登录并保持家庭隔离，图片响应 no-store、nosniff。
4. 只接受真实 JPEG/PNG/WebP，单文件不超过 10 MiB，路径和原文件名不能影响存储位置。
5. 创建、替换和删除均产生脱敏审计；失败不会让数据库指向未写入文件。
6. 容器重建后图片仍存在，数据库和图片卷都有可验证的备份恢复说明与脚本。
7. 自动化、构建和规定移动视口验收全部通过。
